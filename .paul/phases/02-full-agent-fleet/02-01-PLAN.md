<objective>
## Goal
Close the **validate → dedup → evidence tail**: (1) tighten the dedup gate to the
published Phase-2 bar (recall ≥0.95, precision ≥0.90); (2) wire the existing
exact-fingerprint dedup into the Phase-1 verifier so a known duplicate is parked
(status `duplicate`) **before** the oracle runs — no wasted exec, never submitted —
and every validated finding registers its fingerprint (+ embedding) so future
findings dedup against it.

## Purpose
Dedup recall ≥95% is a published Phase-2 success metric and a direct input to the
anti-slop confirmed-rate SLO (02-04). The 01-06 verifier validates + writes evidence
but performs ZERO dedup today — duplicates waste oracle execution and could reach
submission, defeating the "only verified, non-duplicate findings" core value.

## Output
- dedup-mcp: precision calculator + a recall≥0.95/precision≥0.90 gate test (current
  gate is recall≥0.90 only).
- verify_service: pre-oracle exact-duplicate gate (park `duplicate`) + post-validate
  fingerprint & embedding registration, via an injectable in-process dedup adapter
  (control-plane imports dedup-mcp, mirroring how 01-06 imported oracle-mcp).
- validator.md aligned to the real verify_service flow.

  → NO status migration needed; `UPDATE ... SET status='duplicate'` is legal.

## AC-1: Recall / precision gate raised to Phase-2 bar
```gherkin
Given the labeled corpus (recall_fixture.generate_corpus) + network-free BagOfWordsEmbedder
```

## AC-2: Pre-oracle exact-duplicate gate (moat)
```gherkin
Given a hypothesis finding whose exact fingerprint is already registered (is_dup=True)
When verify_finding processes it
Then the finding is updated to status='duplicate'
And the oracle coro is NEVER awaited
And NO evidence is recorded
```

## AC-3: Post-validate fingerprint (+ embedding) registration
```gherkin
Given a hypothesis finding the oracle validates (verdict='validated')
When verify_finding completes
Then evidence is recorded AND status='validated' (unchanged 01-06 ordering)
And the exact fingerprint is registered (idempotent: re-run inserts no second row)
And the finding embedding is stored from the resolved text source
```

## AC-4: Dedup outage is retry-safe (no stranded findings)
```gherkin
Given the pre-oracle dedup check raises a transient error
When verify_finding handles it
Then the claim is released (status back to 'hypothesis') and the error re-raised
  (identical contract to the 01-06 oracle block)
And a post-validate registration failure logs WARNING but does NOT revert 'validated'
```

## AC-5: validator.md ↔ verify_service alignment
```gherkin
Given the real flow (claim → exact-dup gate → oracle → evidence → register fpr+embedding)
When validator.md Execution Plan is read
Then its order matches, with no step the engine does not perform
```

## AC-6: Distinct-parameter findings are NOT collapsed (moat — dedup must never bury a real bug)  <!-- audit-added (must-have A) -->
```gherkin
Given finding A (validated, registered) and finding B on the SAME platform/program/vuln_type/host/path
  but a DIFFERENT vulnerable `parameter`
When B reaches the pre-oracle dedup gate
Then B is NOT parked 'duplicate' — the dedup identity includes `parameter`, so B proceeds to the oracle
And only a finding matching ALL of {platform, program_handle, vuln_type, host, path, parameter} parks as duplicate
```

## AC-7: Deterministic dedup identity + reconstructable duplicate decision  <!-- audit-added (must-have D + strong E) -->
```gherkin
Given the same finding processed twice
When its fingerprint and embedding text are computed
Then both are byte-identical across runs (text source is a FIXED column/composition, not run-dependent)
And when a finding is parked 'duplicate', a structured log records {finding_id, canonical_finding_id, fingerprint}
  so the dedup decision is auditable / post-incident reconstructable
```
