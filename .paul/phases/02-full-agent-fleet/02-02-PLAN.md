<objective>
## Goal
Turn the community sandbox docker-driver from a `GAP-deploy` scaffold (`DockerDriver.run()`
returns `Verdict.ERROR`) into a working, egress-enforced PoC runner: real container execution
with a deny-by-default iptables egress allowlist, a pinned hardened runtime image, and a
fail-closed posture when the egress gate is unreachable.

## Purpose
The sandboxed PoC runner is the execution substrate the exploit-agent (02-03) stands on. The
egress allowlist — derived from the scope JWT, enforced at the network layer, not the prompt
layer — is the platform's core safety invariant: a PoC must never reach a host outside the
authorised scope. Without an enforced allowlist there is no safe way to run attacker-controlled
chains, so the exploit phase stays dark. This plan delivers the community-edition substrate
(docker-driver); Firecracker microVMs remain deferred to Phase 3 (ultraplan task 214).

## Output
- `DockerDriver.run()` / `.snapshot()` implemented (container exec, bounded output, verdict
  mapping, cleanup, fail-closed gate check).
- `bs5-egress-gate` sidecar: per-container deny-by-default iptables, allow only allowlist hosts,
  keyed by container ID; small HTTP register/deregister API at `EGRESS_GATE_URL`.
- `bs5/sandbox-runtime` pinned hardened image (minimal, no shell history / caches).
- `infra/sandbox/` (gate service + runtime image + README) wired into `infra/docker/docker-compose.yml`.
- Unit/integration tests (mocked docker + fake gate); live egress-block proof via human-verify.
</objective>

<acceptance_criteria>

## AC-1: Container execution returns a faithful RunResult
```gherkin
Given SANDBOX_DRIVER=docker and a reachable egress gate
When DockerDriver.run() executes a command (e.g. `echo hello-sandbox`) in a container
Then it returns RunResult with verdict=success, stdout containing the output,
     exit_code=0, and a 64-hex content_hash_hex = sha256(stdout_bytes + stderr_bytes)
And a non-zero exit maps to verdict=crash with the real exit_code
```

## AC-2: Egress is deny-by-default against the allowlist
```gherkin
Given a container whose egress_allowlist contains only allowed.example
When the PoC inside the container attempts to reach a host NOT in the allowlist
Then the connection is blocked at the network layer (iptables, not prompt),
     the attempt is recorded in blocked_egress, and a fully-blocked run reports
     verdict=egress_blocked
And a request to an allowlisted host succeeds
```

## AC-3: Isolation + hygiene
```gherkin
Given any DockerDriver run
When the container executes
Then host env is stripped to a minimal allowlist (PATH only) plus request.env;
     the scope_token, stdin payload, and secrets are NEVER written to the host
     filesystem outside the sandbox boundary;
And when cleanup=true the container is torn down after the run (no orphan containers)
```

## AC-4: Resource bounds hold
```gherkin
Given a runaway PoC
When it emits more than MAX_OUTPUT_BYTES or runs past timeout_sec
Then stdout/stderr capture is capped at MAX_OUTPUT_BYTES (with a truncation marker)
     and a timeout kills the container and returns verdict=timeout
```

## AC-5: Fail-closed on missing/unreachable egress gate
```gherkin
Given SANDBOX_DRIVER=docker
When the egress gate is unset or unreachable at run time
Then DockerDriver.run() refuses LOUDLY (RuntimeError / verdict=error with a clear message)
     BEFORE any container with network access is started
And it NEVER silently falls back to an unenforced-egress container
```

## AC-6: Hardened image + infra wiring
```gherkin
Given the infra/sandbox/ assets
When `docker build` runs against Dockerfile.runtime
Then it produces a pinned, minimal bs5/sandbox-runtime image (curl, jq, python3; no shell
     history, no package caches) that DockerDriver uses as the default container image
And infra/docker/docker-compose.yml gains the bs5-egress-gate service (NET_ADMIN, deny-by-default)
     with EGRESS_GATE_URL exported to the sandbox-mcp service
```
