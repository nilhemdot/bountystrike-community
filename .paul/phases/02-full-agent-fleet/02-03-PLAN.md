<objective>
## Goal
Wire the exploit-agent onto the 02-02 docker-driver sandbox substrate so the
exploit phase can actually run: add the three `exploit_failed_*` finding statuses
the spec writes (currently absent → live `UPDATE` throws), reconcile the
exploit-agent spec from Firecracker wording to the docker substrate, fix the
`result.status`→`result.verdict` API drift, grant the agent the MCP tools it
requires, and make the orchestrator hand `SANDBOX_DRIVER=docker` to the agent's
sandbox-mcp.

## Purpose
02-02 delivered the egress-enforced docker sandbox but nothing drives it. The
exploit-agent is the consumer: it builds a PoC, runs it in the sandbox, captures
a SHA-256 evidence artifact, and flips the finding to `exploit_pending_validation`
for the validator. Today that path is dark on three independent breaks — the DB
rejects the failure statuses, the spec points at a Firecracker driver that does
not exist, and the agent is not granted the sandbox/evidence MCP tools. This plan
closes all three so the orchestrator's existing exploit fan-out (`_exploit_one`)
produces real, evidence-backed findings on the community substrate. Firecracker
stays deferred to Phase 3 (task 214).

## Output
- New migration `13_phase2_exploit_failed_status.sql` adding
  `exploit_failed_oos`, `exploit_failed_timeout`, `exploit_failed_crash` to the
  `finding_status` ENUM (idempotent, positioned by the exploit neighbours).
- `exploit-agent.md` reconciled to the docker substrate (no Firecracker in the
  run path; `SANDBOX_DRIVER=docker`; `result.verdict` not `result.status`; MCP
  tool grants added; Step 8 validator-handoff wording de-Firecrackered).
- `scripts/orchestrator.py::_exploit_one` passes `SANDBOX_DRIVER=docker` +
  `BS_EGRESS_GATE_URL` into the agent env.
- Hermetic test of the orchestrator env wiring + a schema-vs-spec contract
  assertion that the enum carries the `exploit_failed_*` states.
- Live human-verify: a full exploit-agent dry-run through the docker sandbox.
</objective>
