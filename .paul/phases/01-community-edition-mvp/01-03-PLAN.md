<objective>
## Goal
Make the evidence store a production-real, Hatchet-driven write path: fix the boto3≥1.36
checksum break on the R2 client, add a single `EvidenceRecordingService` that atomically
records (blob → `evidence_artifacts` row → hash-chained `audit_log` entry), and expose it
as a durable Hatchet `record-evidence` task triggered through `orchestrator.py`.

## Purpose
"No verification, no submission" is the moat (PROJECT.md). Every validated finding must
land a SHA-256 content-addressable artifact in R2 plus a tamper-evident audit-chain entry,
written durably so a crashed worker cannot leave a finding evidence-less. 01-01 (DB) and
01-02 (Hatchet) shipped the substrate; this plan wires the evidence write path onto it.

## Output
- `R2BlobStore` PUT/GET works against real Cloudflare R2 (checksum config fixed).
- `EvidenceRecordingService.record(...)` — one idempotent call: put blob, upsert artifact
  row, append audit entry; returns `{artifact_id, r2_key, content_hash_hex, chain_hash_hex}`.
- Hatchet `record-evidence` task wrapping the service; registered in `worker.py`.
- `orchestrator.py trigger-record-evidence` seam (mirrors `trigger-heartbeat`).
- Test proving the atomic record path against a mocked R2 (moto) + live Postgres.
</objective>

```gherkin
Given boto3 1.40.61 / aioboto3 15.5.0 are the installed versions (CLAUDE.md trap #5)
When R2BlobStore opens its S3 client
Then the client is configured with request_checksum_calculation="when_required" AND
  response_checksum_validation="when_required" (botocore Config), so a PUT to a
  Cloudflare-R2-compatible endpoint does not attach the default-aws CRC checksum headers R2 rejects

  (not by a moto round-trip alone — moto does NOT reproduce R2's CRC-header rejection, so a

  real trap-#5 gate). A moto put → get round-trip additionally confirms byte fidelity.
```

## AC-2: EvidenceRecordingService records atomically and idempotently
```gherkin
Given a validated finding_id with raw PoC bytes, platform, program_handle, oracle_verdict,
  oracle_method, and scope_token_jti
When EvidenceRecordingService.record(...) is called
Then the blob is stored under its SHA-256 content-addressable R2 key,
  an evidence_artifacts row is inserted (content_hash, finding_id, r2_key, scope_token_jti),
  and a hash-chained audit_log entry is appended via HashChainService (advisory-locked),
  all within a single asyncpg transaction for the two DB writes
And calling record(...) again with byte-identical input does NOT duplicate the artifact row
  (idempotent on content_hash) — the existing artifact_id is returned.
```

## AC-3: R2 write runs durably inside a Hatchet task, triggerable via orchestrator
```gherkin
Given the Hatchet worker is running with the record-evidence task registered
When `python scripts/orchestrator.py trigger-record-evidence ...` triggers the task
Then the task executes EvidenceRecordingService.record(...) on the worker,
  the run reaches SUCCEEDED, and the returned payload carries
  {artifact_id, r2_key, content_hash_hex, chain_hash_hex}
And the artifact is retrievable from the blob store and the audit chain for the finding
  verifies (each entry's chain_hash == sha256(prev_hash || canonical_json(payload))).
```

             so the advisory lock and the artifact insert commit together.
