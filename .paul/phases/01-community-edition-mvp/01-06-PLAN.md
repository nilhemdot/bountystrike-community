<objective>
## Goal
Operationalize the deterministic verifier as a Hatchet `verify-finding` task: load a
`status='hypothesis'` finding, dispatch by `cwe` to the correct pre-built oracle
(XSS / SSRF / SQLi / SSTI / open-redirect), and on an oracle `validated` verdict
record a SHA-256-linked evidence artifact (reusing the 01-03 evidence service) and
transition the finding to `status='validated'`. Any non-`validated` verdict transitions
to `rejected` with **no** evidence artifact.

## Purpose
This is the centerpiece of Phase 1 — "the Moat." The five oracles already exist and
are field-validated (TPR=1.0 / FPR=0.0) in `oracle-mcp`, but nothing in the Phase-1
runtime runs them or links their verdicts to evidence + finding state. This plan wires
01-02 (Hatchet) + 01-03 (evidence store) + the v5 oracles + the 01-01 `findings` schema
into the single durable transition that enforces the project invariant:
**no finding reaches `validated` without an `evidence_artifacts` row.**

## Output
- New `validation` domain in the control-plane (cwe→oracle dispatch + `VerifyFindingService`).
- New `verify-finding` Hatchet v1 task + worker registration + orchestrator trigger seam.
- Unit test suite proving the dispatch table, both verdict branches, the moat invariant,
  the optimistic-claim no-op, and one live oracle field-validation gate.
- `oracle-mcp` added as a control-plane workspace dependency (in-process oracle calls).
</objective>

<acceptance_criteria>

## AC-1: Validated verdict produces evidence + flips status
```gherkin
Given a findings row with status='hypothesis', cwe='CWE-79', a url and parameter
And the dispatched oracle returns an OracleResult with verdict='validated'
When verify_finding runs for that finding_id
Then an evidence_artifacts row is created for that finding_id (content-addressed)
And findings.status becomes 'validated'
And findings.evidence_hash equals the recorded content_hash_hex
And findings.oracle_method equals the OracleResult.oracle_method
```

## AC-2: Non-validated verdict rejects with NO evidence (moat invariant)
```gherkin
Given a findings row with status='hypothesis' and a dispatchable cwe
And the dispatched oracle returns verdict in {unreproducible, flaky, inconclusive}
When verify_finding runs for that finding_id
Then NO evidence_artifacts row is created for that finding_id
And findings.status becomes 'rejected'
And findings.evidence_hash remains NULL
And no finding can ever be left in status='validated' without an evidence_artifacts row
```

## AC-3: cwe → oracle dispatch is correct (5 oracles + legacy aliases)
```gherkin
Given findings whose cwe is one of:
  CWE-79|xss, CWE-89|sqli, CWE-918|ssrf, CWE-1336|"ssti" token, CWE-601|open-redirect
And legacy "<type>-candidate" strings from the recon agent (e.g. "xss-candidate")
When the dispatcher resolves each cwe
Then CWE-79→oracle_xss, CWE-89→oracle_sqli, CWE-918→oracle_ssrf,
     CWE-1336/"ssti"→oracle_ssti, CWE-601→oracle_open_redirect
And "<type>-candidate" is normalised (strip "-candidate") before matching
And generic-injection CWEs that are NOT SSTI-specific (CWE-74 parent injection,
    CWE-94 code injection) resolve to None (unsupported → validation_pending,
    preserved for the Phase-2 RCE path) — they are NOT auto-routed to the SSTI
    oracle, which would mark a real injection bug 'rejected' on an unreproducible
    SSTI probe  <!-- audit-added S3 -->
And the recon "ssti-candidate" bare token still routes to oracle_ssti
```

## AC-4: Unsupported cwe is a safe no-op (no oracle, no evidence)
```gherkin
Given a findings row with status='hypothesis' and a cwe not in the 01-06 set
  (e.g. CWE-639 idor, CWE-78 rce, ssrf-imds, or an unknown string)
When verify_finding runs for that finding_id
Then no oracle is invoked
And no evidence_artifacts row is created
And findings.status becomes 'validation_pending' (awaiting an out-of-scope path)
And a structured log line records the unsupported cwe
```

## AC-5: Optimistic claim — concurrent / already-claimed finding is benign
```gherkin
Given a findings row whose status is not 'hypothesis' (e.g. already 'validated')
When verify_finding runs for that finding_id
Then the optimistic claim UPDATE matches 0 rows
And the task returns a benign no-op result (no oracle, no evidence, no raise)
```

## AC-9: Transient oracle error releases the claim (no silent stranding) <!-- audit-added M1 -->
```gherkin
Given a findings row with status='hypothesis' and a dispatchable cwe
And the CLAIM has already moved it to status='validation_pending'
And the dispatched oracle coroutine RAISES (interactsh down, chromium missing,
    target unreachable, scipy error)
When verify_finding runs for that finding_id
Then the exception is caught, findings.status is reset to 'hypothesis'
     (claim released) with a structured warning "verify.oracle_error"
And the exception is re-raised so Hatchet retries on a re-claimable state
And the finding is NEVER left stranded in 'validation_pending' by a transient error
And no evidence_artifacts row is created and status is never 'validated'
```

## AC-10: Validated verdict with missing scope JTI is parked, not rejected <!-- audit-added M2 -->
```gherkin
Given a findings row whose job_id is NULL or whose scan_jobs.scope_jwt_jti is NULL/empty
And the dispatched oracle returns verdict='validated'
When verify_finding runs for that finding_id
Then record() is NOT called with an empty scope_token_jti (it would raise ValidationError)
And findings.status remains 'validation_pending' (parked, claimed, recoverable)
And findings.status is NOT set to 'rejected' (a provenance gap must never terminally
    bury a real, oracle-confirmed bug or corrupt the confirmed-rate metric)
And a structured warning "verify.missing_scope_jti" is logged with the finding_id
And no evidence_artifacts row is created (jti unresolved)
```

## AC-11: Missing oracle input (null url/parameter) is a safe no-op <!-- audit-added S1 -->
```gherkin
Given a findings row with status='hypothesis' and a dispatchable cwe
And findings.url or findings.parameter is NULL/empty
When verify_finding runs for that finding_id
Then the oracle coroutine is NOT invoked with None/"" (it requires a non-empty param)
And findings.status remains 'validation_pending' (parked) with warning
    "verify.missing_oracle_input"
And no evidence_artifacts row is created and status is never 'validated'
```
