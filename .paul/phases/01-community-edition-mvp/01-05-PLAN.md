<objective>
## Goal
Deliver `scope_changes` diff events to a generic outbound webhook so a self-hosted
operator is alerted when a watched program's scope, payout, or status changes —
closing the gap left by 01-04 (events are persisted but never leave the DB).

## Purpose
Phase 1 Community Edition MVP requires a scope-change *signal*, not just a log
row. A solo hunter cannot poll Postgres by hand; the webhook (Slack/Discord
incoming-webhook compatible, or any JSON consumer) is the MVP delivery channel.
This is the "channel for ScopeChanged events" that ROADMAP carved out of old
01-04.

## Output
- New additive SQL migration adding `scope_changes.notified_at` (delivery
  high-water mark) + a partial index on undelivered rows.
- `ScopeNotificationService` — selects undelivered events, POSTs a webhook
  payload, marks rows delivered atomically.
- `scope_poll` task wired to deliver new events at the end of every poll run.
- Unit tests proving delivery, failure-redelivery, no-op-when-unconfigured, and
  idempotency.
</objective>

<acceptance_criteria>

## AC-1: New events delivered to webhook
```gherkin
Given SCOPE_WEBHOOK_URL is configured
  And one or more scope_changes rows have notified_at IS NULL
When the notification service runs
Then one or more HTTP POSTs (bounded batches, see AC-7) are made to the webhook,
     each with a JSON body containing a length-capped human-readable summary and
     an events array (one entry per delivered change in that batch)
  And on a 2xx response every row in that batch has notified_at set to now()
```

## AC-2: Delivery failure leaves rows redeliverable
```gherkin
Given undelivered scope_changes rows exist
When the webhook returns a non-2xx status or the POST raises (timeout/connection)
Then no row is marked notified_at
  And the service returns 0 delivered and does not raise
  And the next run re-attempts delivery of the same rows
```

## AC-3: No-op when webhook unconfigured
```gherkin
Given SCOPE_WEBHOOK_URL is empty or unset
When the notification service runs
Then no HTTP request is made
  And the service returns 0 delivered
  And scope ingestion / scope_poll completes unaffected
```

## AC-4: Already-delivered rows are never re-sent
```gherkin
Given scope_changes rows whose notified_at is already set
When the notification service runs
Then those rows are excluded from the payload
  And only rows with notified_at IS NULL are considered
```

## AC-5: Migration is additive and idempotent
```gherkin
Given the live bs-postgres scope_changes table from 01-01/01-04
When infra/sql/12_phase1_scope_notified.sql is applied
Then a nullable notified_at TIMESTAMPTZ column and a partial undelivered-row
     index exist
  And re-applying the migration is a no-op (no error)
  And the ScopeChange ORM model exposes notified_at
```

<!-- audit-added AC-6..AC-9 -->

## AC-6: Pre-existing events are NOT retro-delivered (go-forward only)
```gherkin
Given the live scope_changes table already holds historical rows from 01-04
     (the first projectdiscovery poll alone seeded ~4104 rows)
When migration 12 is applied
Then every row that existed before the column was added is stamped
     notified_at = now() (backfilled as "already delivered")
  And the first delivery run after deploy sends ONLY events detected after the
     feature went live — it does NOT flood the webhook with thousands of stale
     historical changes
```

## AC-7: Batch size and payload-size bounds (Discord/Slack safe)
```gherkin
Given more undelivered events exist than fit one provider-safe payload
When the notification service runs
Then each POST carries at most BATCH_SIZE events (default 25)
  And the rendered summary string (text/content) stays within the strictest
     provider cap (Discord content ≤ 2000 chars) — overflow is summarised
     ("N changes; first M shown") not truncated mid-payload
  And the service loops, delivering successive batches within the same run,
     until the backlog is drained or a per-run cap (max batches / wall-clock) is
     hit — it does NOT leave a large backlog to dribble out one batch per 6h poll
```

## AC-8: At-least-once delivery; redelivery window is bounded and documented
```gherkin
Given a batch was POSTed and the webhook returned 2xx
When the notified_at UPDATE or commit fails (DB error / task crash) before it persists
Then those rows remain notified_at IS NULL and are redelivered on the next run
  And this is accepted as at-least-once semantics (duplicate notification, never
     silent loss) — the plan claims at-least-once, NOT exactly-once
```

## AC-9: Delivery failure is observable, never silent
```gherkin
Given undelivered events exist and the webhook is misconfigured or unreachable
When the notification service runs
Then a structured WARNING is logged with the HTTP status (or error class) and the
     count of events still pending — the secret-bearing URL is NOT logged in full
  And scope_poll's return dict surfaces both delivered and still-pending counts
     so "0 new events" is distinguishable from "delivery broken, N pending"
```

    - `BATCH_SIZE = 25` events per POST. The summary string MUST stay within the

      an over-length string. Full detail always rides `events[]` (providers
      ignore unknown keys; generic consumers parse it).
    <!-- audit-added M3: webhook URL is a secret -->
    - SCOPE_WEBHOOK_URL is secret-bearing (Slack/Discord embed an auth token in
      the path). NEVER log, return, or include the full URL in exceptions or the
      Hatchet result. Redact to scheme+host only in any log line.
    - `async def deliver_pending(session, *, batch_size: int = BATCH_SIZE,
       max_batches: int = 50) -> dict[str, int]` returning
       `{"notified": <delivered>, "pending": <still-undelivered>}`:
      1. If no/invalid webhook URL → log info (redacted), return {notified:0,
         pending: <count WHERE notified_at IS NULL>} (AC-3, AC-9).
      2. Loop up to max_batches (drain, AC-7):
         a. SELECT scope_changes WHERE notified_at IS NULL ORDER BY id
            LIMIT :batch_size **FOR UPDATE SKIP LOCKED** (S1: concurrent/overlapping
            runs — cron + manual trigger — never double-send the same rows).
            If none → break.
         b. Build payload; capture ids.
         c. POST via httpx.AsyncClient(timeout=10). Retry policy (S2): retry ONCE
            on transport error OR HTTP 429/5xx (single short backoff). Treat 4xx
            (except 429) as permanent failure for this batch.
         d. On failure (post-retry): log WARNING with status/error-class + pending
            count (URL redacted, M3/AC-9); break the loop WITHOUT marking
            (AC-2); leave rows for next run.
         e. On 2xx: `UPDATE scope_changes SET notified_at = now()
            WHERE id = ANY(:ids)`, commit, add to delivered count (AC-1).
      3. Return {notified, pending=<remaining count WHERE notified_at IS NULL>}.
    <!-- audit-added M4: at-least-once is the contract -->
    - At-least-once delivery: a crash/DB-error between the 2xx and the committed
      notified_at UPDATE redelivers that batch next run (duplicate, never silent
      loss). Document this in the module docstring (AC-8). Do NOT claim
      exactly-once.
    - Keep delivery fail-open: wrap the body so a webhook outage or DB error never
      crashes scope_poll (the scope_poll call site also guards, S3).
    Export `deliver_pending` from services/__init__.py and re-export from the
    domain __init__.py alongside detect_scope_changes.
    Avoid: blocking requests lib (use httpx); marking rows before the 2xx
    confirms; reading env at module import (breaks test monkeypatch + 12-factor);
    logging the raw URL; one giant POST of the whole backlog.
  </action>

- Webhook channel ONLY. No SMTP/email, no Discord-specific embed formatting, no UI — explicitly deferred.
- No per-program / per-operator routing or event filtering: all undelivered events go to the single global SCOPE_WEBHOOK_URL.
- No new third-party dependency — httpx is already a project standard (httpx.AsyncClient).
- Secrets = env var only (no secret-store integration this plan).
- No standalone notify Hatchet task — delivery rides the existing scope_poll run (per locked decision).
