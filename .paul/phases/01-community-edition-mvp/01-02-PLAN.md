**Phase:** 01-community-edition-mvp

**Status:** PLAN (not yet applied)
**Depends on:** 01-01 (bs-postgres:pg17 + infra/docker-compose.yml). Hatchet engine was explicitly deferred to this plan.

---

## Objective

Stand up the Hatchet v1 self-hosted engine in `infra/docker-compose.yml` and
define the first BountyStrike workflow task using the **v1 function-based task
API**, driven from the FastAPI control-plane. One `hatchet` worker process
registers an async task, the engine accepts a triggered run, and the run
reaches `SUCCEEDED` against live Postgres — proven empirically, not by import.

This establishes the durable-execution backbone every later agent invocation
(recon → scan → exploit → validate → report) rides on.

---

## Context

- **CLAUDE.md trap #2 (authoritative):** Hatchet v1 (sdk ≥ 1.33.5) is
  **function-based** — `@hatchet.task()`, **NOT** the legacy
  `@hatchet.workflow` class API. Task inputs are **Pydantic models**. Async
  handlers use the **`aio_` prefix** convention (`aio_run`, etc.). The SDK
  client is created once and shared.
- Hatchet self-hosted needs its **own Postgres + RabbitMQ** per upstream
  compose; do **not** point its engine at the BountyStrike app DB
  (`bs-postgres`). Keep app data and engine data isolated.
- Control-plane is FastAPI + DDD (`control-plane/`). The worker is a separate
  process from the API; both import the shared Hatchet client.
- `scripts/orchestrator.py` is the existing hunt entry point — the trigger
  call (`aio_run` / `aio_run_no_wait`) is wired here.
- Pin the Hatchet engine image to a fixed tag (no floating/moving tags — same
  pin doctrine as 01-01) and the `hatchet-sdk` to a fixed version in the
  dependency manifest.

## Tasks

### Task 1 — Pin + install hatchet-sdk
- Add `hatchet-sdk` at a fixed version to the dependency manifest (root/workspace `pyproject.toml`).
- `uv lock && uv sync`; capture resolved version into the SUMMARY.
- **Verify:** `uv run python -c "import hatchet_sdk; print(hatchet_sdk.__version__)"` exit 0.

### Task 2 — Hatchet engine in compose
- Add the self-hosted Hatchet engine + its dedicated Postgres + RabbitMQ to `infra/docker-compose.yml`, **pinned image tags**, on the existing network. Do not reuse `bs-postgres`.
- Surface the engine token / address as env (gitignored `.env`, same pattern as 01-01).
- **Verify:** `docker compose -f infra/docker-compose.yml config` valid; engine container reaches healthy.

### Task 3 — First v1 task + worker + trigger
- Define a Hatchet client (single shared instance) + one `@hatchet.task()` with a Pydantic input model and an `aio_`-prefixed async handler (a trivial echo/heartbeat task is sufficient — this plan proves the runtime, not business logic).
- Add a worker entry point that registers the task.
- Wire a trigger seam into `scripts/orchestrator.py` (`aio_run` / `aio_run_no_wait`).
- **Verify (empirical, live engine):** start worker → registration logged; trigger the task → run reaches `SUCCEEDED`.

## Boundaries

- **No** business-logic edits inside `control-plane/domains/` beyond the thin trigger/wiring seam.
- **No** evidence-store / R2 work — that is 01-03.
- **No** real agent logic in the task — heartbeat/echo only; agent tasks land in later plans.
- Engine data store stays isolated from `bs-postgres`.
- Honor pin doctrine: no floating/moving image tags, no unpinned sdk.
